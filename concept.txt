# AEGIS — Концепция (v2)

> Документ самодостаточен: его можно целиком передать разработчику или LLM и начинать работу с Phase 0 из `roadmap.txt`.

---

## 0. Миссия

**AEGIS** — автономная монолитная система, которая:

1. **Максимально полно восстанавливает** внешний цифровой периметр организации (пассивно и активно).
2. **Ведёт собственную историю** всего, что видит: граф активов со временем («машина времени»).
3. **Непрерывно мониторит** периметр и сообщает только о значимых изменениях.
4. **Оценивает риск** по открытым данным (CVSS, EPSS, KEV, контекст актива).
5. **Объясняет** всё через локальную LLM, с цитированием доказательств.
6. **Проверяет исправление** повторной разведкой.

Не SIEM. Не EDR. Не DDoS-защита. Не очередной Shodan.
Это «глаза и мозг», работающие снаружи. Рук (автоматического воздействия на инфраструктуру клиента) нет.

## 1. Жёсткие принципы

| Принцип | Что это значит на практике |
|---|---|
| **Agentless, zero footprint** | Ничего не ставится у клиента. Нет постоянного доступа, нет хранимых учётных данных клиента, нет обратных каналов. Единственное допустимое «касание» — TXT/файл подтверждения владения (опционально, удаляется). |
| **Бюджет $0** | Только бесплатные API, открытые датасеты, open-source тулзы. Ни одна функция не должна требовать платной подписки. Платные источники могут быть *опциональными* щупальцами, но не основой. |
| **LLM обязательна** | Локальная (Ollama). Работает в трёх местах: генерация гипотез в разведке, классификация неизвестного, аналитик (объяснения, дайджесты, чат). Без LLM система должна запускаться, но считается «неполной». |
| **LLM ≠ источник истины** | Она не создаёт findings, не меняет статусы, не имеет инструментов с побочными эффектами. Все её утверждения проверяются на наличие ссылок на реальные `Observation`. |
| **Scope-first** | Активные действия только по активам со статусом `IN_SCOPE` (раздел 3). Пассивная разведка — по всему. |
| **Вежливость и прозрачность** | Фиксированный известный IP/ASN источника, честный User-Agent со ссылкой на контакт/opt-out, rate-limit на каждый хост, уважение robots.txt для краулера. Никакой ротации прокси и обхода блокировок: нас заблокировали — значит, нас заблокировали. |
| **Только безопасные проверки** | Без эксплуатации, без brute-force по учётным данным, без DoS/fuzz-шаблонов, без скачивания содержимого найденных ресурсов. Проверяем *наличие*, не забираем *данные*. |
| **Монолит** | Один процесс, один репозиторий, один `docker compose`. Модульность — внутри пакета, не по сервисам. |

## 2. Модель «Осьминог»: мозг и щупальца

```
                       ┌──────────────────────────┐
                       │          МОЗГ            │
                       │  scope · граф · история  │
                       │  baseline · risk · LLM   │
                       └────────────┬─────────────┘
          ┌──────────┬──────────┬───┴──────┬───────────┬──────────┐
          ▼          ▼          ▼          ▼           ▼          ▼
       CT-логи     DNS       RDAP/BGP   HTTP/TLS    порты    GitHub/Archive
      (пассив.)  (смеш.)    (пассив.)  (актив.)   (актив.)    (пассив.)
```

**Щупальце (Tentacle)** — плагин-коллектор с единым контрактом:

```python
class Tentacle:
    name: str
    mode: "passive" | "active"
    requires_scope: bool            # active => True
    quota: Quota                    # лимиты запросов/сутки, rate per host
    def run(self, target: Asset|Seed) -> Iterable[ObservationCandidate]: ...
    def health(self) -> SourceHealth  # жив? лимит исчерпан? ToS/лицензия?
```

Правила:
- Щупальце **ничего не решает** — возвращает кандидатов в наблюдения с сырым доказательством.
- Мозг сам решает, что записать, как скоррелировать и что запускать дальше.
- Каждое щупальце регистрируется в **реестре источников** (`SourceRegistry`): тип, лимиты, условия использования/лицензия, статус здоровья. Лимиты бесплатных API меняются — реестр это учитывает, а не код.
- Падение/закрытие источника = пометка `degraded`, не ошибка системы.

Готовые open-source тулзы подключаются как щупальца-обёртки (subprocess + разбор вывода), а не переписываются. Свои лёгкие щупальца пишем там, где это просто (DNS, TLS, HTTP-проба).

## 3. Scope и авторизация

Каждый найденный актив получает статус принадлежности:

| Статус | Значение | Что разрешено |
|---|---|---|
| `VERIFIED` | Владение подтверждено (seed владельца, TXT `aegis-verify=…`, файл `/.well-known/aegis-verify`, либо флаг `self` для собственных активов оператора) | Всё: пассивная + активная разведка, безопасные проверки |
| `CANDIDATE` | Предположительно принадлежит организации (атрибуция по корреляции) | Только пассивная; активное — после подтверждения оператором |
| `THIRD_PARTY` | Чужое: CDN, облачный провайдер, SaaS, регистратор | Только пассивная; фиксируем как зависимость (`depends_on_vendor`) |
| `OUT_OF_SCOPE` | Явно исключено оператором | Ничего |

Правила:
- **Активные щупальца отказываются запускаться** по активу не-`VERIFIED`. Проверка на уровне ядра, а не в каждом плагине.
- IP-адреса общих хостингов/CDN не сканируются, даже если на них резолвится домен цели: сначала определяется принадлежность диапазона (RDAP/ASN).
- Расширение разведки (pivoting) идёт по связям, но с **лимитом глубины** и **стоп-листом** (облачные и CDN-провайдеры, крупные SaaS), иначе обход «разрастается» до всего интернета.
- Атрибуция имеет собственную уверенность (`attribution_confidence`), отдельную от уверенности существования (`existence_confidence`): «хост существует» и «хост принадлежит цели» — разные вопросы.

## 4. Разведка

Разведка — ядро продукта. Мониторинг — это повторяемая разведка плюс сравнение с историей.

### 4.1. Итеративный цикл

```
seed ─► пассивный сбор ─► нормализация ─► атрибуция ─► новые seeds
                                              │
                                              ▼
                      активная проверка (только VERIFIED) ─► граф
                                              │
                                              └──► повтор, пока есть новое (с лимитом глубины)
```

### 4.2. Пассивные щупальца (бесплатные)

| Что | Источник | Что даёт | Примечание |
|---|---|---|---|
| Certificate Transparency | crt.sh (JSON), прямой опрос CT-логов; live-стрим, если доступен публичный инстанс | Поддомены, история сертификатов, новые выпуски | crt.sh бывает нестабилен: кэш, ретраи, бэкофф |
| DNS | Публичные резолверы (несколько) + свой кэширующий резолвер (unbound) | A/AAAA/CNAME/MX/NS/TXT/SOA/CAA, сравнение ответов разных резолверов | **Собственная история DNS** копится с первого дня (платной passive DNS нет) |
| RDAP/WHOIS | RDAP через IANA bootstrap | Владелец диапазона/домена, даты, NS, регистратор | Кэшировать: лимиты |
| BGP/ASN | RIPEstat Data API, Team Cymru IP→ASN (DNS), PeeringDB | ASN, префиксы, принадлежность | Основа атрибуции IP |
| Internet datasets | Shodan InternetDB (бесплатный, по IP), Wayback CDX, Common Crawl index | Порты/CPE/известные CVE по IP; исторические URL и поддомены | Условия использования проверять отдельно, особенно при коммерческом применении |
| Код | GitHub API (бесплатный токен), поиск по домену | Упоминания хостов, конфигов; **утечки секретов фиксируем фактом и местом, значение маскируем** | Строгие лимиты |
| Репутация | abuse.ch (URLhaus и др.), DNSBL (низкий объём) | Домен/IP в фидах вредоносной активности, чёрных списках | Часть фидов требует бесплатный ключ |
| Takeover-отпечатки | Открытая база can-i-take-over-xyz | Признаки dangling CNAME на незанятые сервисы | Вывод — только после активной проверки |

Платные/ограниченные сервисы (Censys, SecurityTrails, VirusTotal и т. п.) — **опциональные** щупальца, если у оператора есть бесплатная квота. Ядро на них не опирается.

### 4.3. Активные щупальца (только `VERIFIED`)

| Что | Как | Примечание |
|---|---|---|
| DNS-перебор | subfinder/dnsx + свои пермутации; открытые словари (SecLists, Assetnote) | Wildcard-детект обязателен |
| Порты | naabu / nmap (SYN или connect), top-1000 TCP по умолчанию, полный диапазон — редко и по решению оператора | Лицензия nmap ограничивает встраивание в коммерческий продукт — учесть, если будет коммерциализация |
| TLS | свой зонд (ssl/tlsx): цепочка, SAN, CA, сроки, протоколы, шифры | |
| HTTP | свой зонд (httpx-подобный): заголовки, редиректы, title, favicon-hash, методы | Безопасные заголовки, cookies-флаги |
| Технологии | сигнатуры по заголовкам/HTML/favicon | Версия → кандидат на CPE, не готовый вывод |
| Краулер | katana-подобный, ограниченная глубина, robots.txt, задержки | Не обходим ограничения |
| Безопасные проверки | nuclei только безопасных категорий (технологии, экспозиции, мисконфиги, детект CVE без эксплуатации) | Без intrusive/dos/fuzz шаблонов |
| Экспозиции файлов | Проверка наличия типовых путей (`/.git/`, `/.env`, бэкапы) по статусу/сигнатуре | **Содержимое не сохраняем** |
| Почтовая политика | MX, SPF, DKIM (по распространённым селекторам), DMARC, MTA-STS | Без SMTP-энумерации пользователей |
| Облачные ресурсы | Проверка кандидатов (имена, производные от организации) на публичную доступность корня бакета | Листинг корня/HEAD, **без скачивания объектов** |
| Lookalike/typosquat | Генерация вариантов написания бренда/домена + DNS-резолв + CT | Мониторинг, а не атака на третьих лиц |

Каждая активная проба сохраняет сырое доказательство (запрос/ответ/метаданные) в хранилище доказательств с хэшем.

### 4.4. Уверенность и корреляция

- Актив, подтверждённый **двумя независимыми классами источников** (например, CT + активный DNS), получает высокую уверенность существования.
- Один пассивный источник без подтверждения = `LOW`, ставится в очередь на проверку (если актив `VERIFIED` по доменной принадлежности).
- Независимость считается по *классам* (CT / DNS / BGP / internet-датасеты / код / активная проба), а не по числу API: три агрегатора одних и тех же данных — это один источник.

### 4.5. Что намеренно НЕ делаем в разведке

Парсинг соцсетей и вакансий, базы утечек учётных данных, даркнет и Telegram-каналы, SMTP VRFY/EXPN, перебор учётных данных, обход защит, ротация прокси. Юридически и этически это зона риска, а ценности для внешнего периметра мало. Если какая-то из этих тем понадобится — отдельное решение с юридической проверкой.

## 5. LLM в разведке (где она реально полезна)

1. **Генерация кандидатов.** По уже найденным именам (`api-eu`, `stg-payments`, `vpn2`) LLM предлагает вероятные соседние имена и шаблоны именования. Предложения идут в очередь *проверки DNS* — это гипотезы, а не факты.
2. **Классификация неизвестного.** По нормализованным признакам HTTP-ответа (title, заголовки, favicon-hash, фрагмент обрезанного текста) LLM предполагает: «панель входа X», «страница по умолчанию», «внутренний инструмент». Результат помечается `llm_hypothesis` с уверенностью и не влияет на risk без подтверждения.
3. **Подсказки по атрибуции.** LLM может указать, что два хоста похожи по именованию/сертификатам/хостингу, чтобы поднять кандидата в очередь ручной проверки. Решение остаётся за правилами и оператором.

## 6. Граф активов во времени

### 6.1. Вершины
`Organization`, `Domain`, `Subdomain`, `IP`, `ASN`, `CIDR`, `Certificate`, `Port/Service`, `Technology`, `Software`, `CVE`, `CloudResource`, `ExternalEntity` (CDN, SaaS, регистратор, облако), `RepoLeak`, `LookalikeDomain`.

### 6.2. Рёбра (временные)
`resolves_to`, `subdomain_of`, `belongs_to_asn`, `hosts_service`, `uses_certificate`, `issued_by_ca`, `runs_technology`, `has_vulnerability`, `sends_mail_via`, `depends_on_vendor`, `attributed_to`.
У каждого ребра: `first_seen`, `last_seen`, `confidence`, ссылки на наблюдения.

### 6.3. `Observation` — единственная лента событий

```python
Observation:
  id, asset_id, timestamp, source, source_class,
  property,             # "ip", "cert_fingerprint", "http_title", "open_port" ...
  old_value, new_value, # jsonb
  confidence,           # 0..1
  evidence_ref,         # путь/хэш сырого доказательства
  ttl                   # когда считать наблюдение устаревшим
```

**Правило записи (важно для объёма данных):** новое наблюдение создаётся только при *изменении* значения. Если значение то же — обновляется `last_confirmed` у текущего состояния. Иначе ежечасный опрос за год превращается в гигабайты одинаковых строк.

### 6.4. Машина времени
Состояние любого актива на любую дату = последнее наблюдение каждого свойства на эту дату. Diff двух дат = список наблюдений между ними.

### 6.5. Хранилище
PostgreSQL (JSONB) — единственная БД: активы, рёбра, наблюдения, findings, очередь задач. Граф — таблицами; для анализа путей — `networkx` в памяти. Отдельная графовая БД не нужна. Сырые доказательства — файловая система (сжатие, хэш, срок хранения).

## 7. Мониторинг

### 7.1. Каденции (настраиваются по критичности актива)

| Что | Частота по умолчанию |
|---|---|
| CT/новые сертификаты | каждые несколько часов |
| DNS-записи ключевых активов | каждый час / каждые несколько часов |
| HTTP/TLS-пробы | раз в сутки (ключевые — чаще) |
| Порты top-1000 | раз в неделю |
| Полное сканирование портов | по решению оператора, редко |
| Новые поддомены (перебор) | раз в неделю |
| Lookalike-домены | раз в сутки/неделю |
| RDAP (сроки, NS) | раз в сутки |
| Репутационные фиды | раз в сутки |

### 7.2. Типы изменений (источники findings)

- Новый/исчезнувший актив, новая связь.
- Новый открытый порт/сервис; смена технологии или версии.
- Сертификат: новый CA, подозрительная частота перевыпуска, истечение, несовпадение имени.
- DNS: смена NS, A/CNAME на новый ASN, dangling CNAME (кандидат на takeover).
- Появление чувствительных экспозиций (админ-панели, `.git`, `.env`, публичные бакеты).
- Почтовая политика: исчезла/ослабла DMARC/SPF.
- Срок действия домена/сертификата.
- Новый lookalike-домен с живым резолвом/сертификатом.
- Находка в публичном коде (маскированный секрет, упоминание внутреннего хоста).
- Репутация: актив появился в вредоносных фидах/чёрных списках.

### 7.3. Мониторинг доступности (вместо «детекта DDoS»)

Честное ограничение: снаружи **нельзя** отличить атаку от сбоя, деплоя или проблем хостера. Поэтому система не объявляет «DDoS», а фиксирует наблюдаемые факты:

```
REACHABILITY_LOSS       цель перестала отвечать (TCP/HTTP/DNS)
LATENCY_DEGRADATION     время ответа выросло относительно baseline
TLS_FAILURE             рост ошибок рукопожатия
HTTP_ERROR_SPIKE        рост 5xx/таймаутов в наших пробах
DNS_ANOMALY             неожиданные изменения/задержки DNS
```

LLM формулирует гипотезы («совместимо с перегрузкой, в том числе атакой; нужны серверные метрики») и явно указывает, чего не знает. Точки наблюдения: на старте одна (ваш хост); вторая и далее — по возможности бесплатно, чтобы отличать «не видно из моей сети» от «не видно вообще».

## 8. Baseline

Первичная разведка собирает исходное состояние (обычно 7–14 дней, чтобы поймать «медленные» ресурсы). Baseline — это не только снимок, но и статистика изменчивости:

- число активов по типам, типичные порты/технологии/CA/ASN;
- скорость изменений (сколько новых поддоменов в день — медиана и разброс);
- типичные времена ответа (p50/p95) по ключевым хостам.

**Начинаем с правил и простых robust-статистик (медиана, MAD).** Сложный ML для внешних данных избыточен: изменения редкие, правила и пороги дают нужное качество. «Новый актив вне нормы» = отклонение от личной истории организации.

## 9. Risk Engine (только открытые данные)

Источники: NVD (бесплатный ключ), CISA KEV, FIRST EPSS (ежедневный файл), OSV.dev, открытые наборы эксплойтов/PoC (поиск на GitHub, Exploit-DB).

**Класс доказательства** — обязателен для каждого finding:

| Класс | Значение |
|---|---|
| `CONFIRMED` | Подтверждено активной безопасной проверкой |
| `PROBABLE` | Версия/баннер совпали с уязвимой, но не проверено активно |
| `POSSIBLE` | Косвенный источник (сторонний датасет, устаревшие данные) |

Приоритет = функция от: класса доказательства, CVSS, EPSS, KEV, критичности актива (публичная экспозиция, админ-панель, роль), наличия публичного PoC, давности. Вывод: `CRITICAL/HIGH/MEDIUM/LOW/INFO` плюс **разложение причин** (почему именно так). Совпадение версии без подтверждения никогда не выше `HIGH`.

## 10. AI Analyst (локальная LLM)

### 10.1. Роль
Переводит детерминированные факты в понятный язык и помогает оператору задавать вопросы к графу. Не источник истины.

### 10.2. Что умеет
- **Дайджест** «что изменилось за сутки/неделю и что важно».
- **Объяснение finding**: что, почему важно, что изменилось, что проверить первым.
- **Чат поверх графа**: «что появилось после 3 октября?», «какие хосты с админ-панелью видны снаружи?», «покажи историю vpn.example.com».
- **Executive summary** для нетехнического читателя.
- **Помощь в разведке** (раздел 5).

### 10.3. Как устроено безопасно

1. **Вход — только структурированные факты.** LLM получает нормализованный finding и ограниченный набор полей, не сырые HTTP-страницы.
2. **Данные из интернета недоверенные (prompt injection).** Title, баннеры, тексты страниц могут содержать инструкции для модели. Поэтому: поля обрезаются и экранируются, оборачиваются как данные, а у LLM **нет инструментов с побочными эффектами** (нет запуска сканов, записи в БД, сетевых запросов, смены статусов).
3. **Чат работает через белый список read-only функций** (`get_asset`, `list_changes(since)`, `list_findings(filter)`, `asset_history(id)`), а не через произвольный SQL. Естественный язык превращается в вызов функции с проверяемыми параметрами.
4. **Цитирование и проверка.** Каждое утверждение в ответе обязано ссылаться на `Observation`/`Finding` ID. Пост-валидатор проверяет: ID существуют, числа и даты в тексте совпадают с данными. Не прошло — ответ помечается или переделывается.
5. **Нет данных — так и говорим.** Модель обязана отвечать «в данных нет», а не додумывать.

### 10.4. Модель и железо
Ollama, модель задаётся в конфиге. Если хватает памяти (порядка 16 ГБ) — gpt-oss 20B или аналог; на слабом железе — модель класса 7–8B (Qwen, Llama, Gemma и т. п.) с более жёсткими шаблонами. Архитектура не привязана к конкретной модели. **Первое, что проверяется в Phase 0, — какая модель реально тянется на вашем железе и с какой скоростью.**

## 11. Верификация исправлений

```
1. Оператор помечает finding «исправлено»
2. Планировщик запускает целевую повторную разведку именно по этому активу
3. Сравнение новых наблюдений с состоянием на момент finding
4. Проблема исчезла → verified; нет → re-open с пометкой «исправление не подтвердилось»
```
Верифицируется только то, что видно снаружи (порт закрыт, сертификат заменён, путь больше не отдаётся).

## 12. Доставка и оповещения (бесплатно)

Telegram-бот, e-mail через свой SMTP/почтовый аккаунт, webhook, файловые отчёты (Markdown/HTML/PDF). Веб-интерфейс — лёгкий (FastAPI + HTMX или простая SPA), раздаётся из того же процесса. Главный экран: статус, изменения за сутки, топ-риски, окно аналитика. Не SIEM-свалка: меньше, чем N значимых элементов в день, остальное — в «шуме» по запросу.

## 13. Стек и структура

```
Runtime:     Python 3.12+, один процесс
API/UI:      FastAPI (+ HTMX или статический SPA)
БД:          PostgreSQL (JSONB) — активы, рёбра, наблюдения, findings, очередь
Очередь:     таблица задач в Postgres (SELECT … FOR UPDATE SKIP LOCKED) — без Redis на старте
Планировщик: APScheduler внутри процесса
LLM:         Ollama (локально)
Доказательства: файловая система (сжатие, SHA-256)
Деплой:      docker compose (app + postgres + ollama)
```

```
aegis/
├── main.py            # запуск, сборка зависимостей
├── config.py          # настройки, реестр источников
├── db/                # модели, миграции (alembic)
├── core/
│   ├── scope.py       # статусы принадлежности, авторизация
│   ├── graph.py       # активы, рёбра, машина времени
│   ├── observe.py     # правило записи, нормализация
│   ├── baseline.py
│   ├── monitor.py     # каденции, diff, findings
│   ├── risk.py
│   ├── verify.py
│   └── analyst.py     # LLM: промпты, функции, валидатор цитат
├── tentacles/         # passive/*, active/* (по файлу на щупальце)
├── web/               # API + интерфейс
└── tests/
```
Redis добавляется только если очередь на Postgres перестанет справляться — это не будет раньше, чем на сотнях целей.

## 14. Анти-скоуп (чего НЕ делаем)

- ❌ Клиентские агенты, сенсоры, любое ПО у клиента
- ❌ Приём логов клиента, SIEM/EDR/XDR
- ❌ Автоматическое воздействие на инфраструктуру клиента (WAF, firewall, CDN)
- ❌ Эксплуатация уязвимостей, подбор паролей, DoS/нагрузочные «проверки»
- ❌ Ротация прокси и обход блокировок
- ❌ Утечки учётных данных, даркнет, закрытые каналы
- ❌ Заявления «защитим от DDoS» (только наблюдаемые факты о доступности)
- ❌ Multi-tenant SaaS на старте
- ❌ Платные подписки как зависимость ядра
- ❌ Собственный Internet-wide сканер (мы смотрим на цели, а не на весь интернет)

## 15. Нефункциональные требования

- **Нагрузка на цели:** лимиты на хост и общий бюджет запросов; настраиваемые окна сканирования.
- **Секреты:** API-ключи только в окружении/секрет-хранилище; в доказательствах секреты маскируются.
- **Хранение доказательств:** сроки, сжатие, возможность полного удаления данных организации.
- **Журнал действий:** каждый активный запуск фиксируется (кто, по какому активу, на каком основании scope).
- **Устойчивость:** корректное завершение, повтор задач, деградация при падении источников.
- **Тесты:** щупальца тестируются на записанных ответах; ядро — на синтетических графах.
